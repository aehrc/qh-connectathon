Referral Server (referrals, tasks, booking) https://referrals.efiq.hospservices.net/fhir HAPI with the Radiology Referral and Booking IG, AU eRequesting and AU Core, plus the AU Patient Summary Patient/[id]/$summary operation (below). Open, no auth.

The directory and the referral server are separate servers with separate data. Directory ids start with qhd-, referral ids with qhc-.

Open the collection and work through the folders in order, or use the Collection Runner for a full pass. Folders 2 to 5 chain together: the ids created by one request are saved for the next.

The requests in curl

If you prefer a terminal. X-Request-ID is required by the directory.

DIR=https://directory.efiq.hospservices.net/fhir
REF=https://referrals.efiq.hospservices.net/fhir
RID=$(uuidgen)

# D-01  CT services in Queensland, with Location and Organization
curl -H "X-Request-ID: $RID" \
  "$DIR/HealthcareService?service-type=http://snomed.info/sct|310128004&location.address-state=QLD&_include=HealthcareService:location&_include=HealthcareService:organization"

# D-02  from the service to its Endpoints
curl -H "X-Request-ID: $RID" \
  "$DIR/HealthcareService?_id=qhd-hcs-01&_include=HealthcareService:endpoint&_include=HealthcareService:organization"

# T-01  new work for a filler, with the ServiceRequest
curl "$REF/Task?owner=qhc-org-fill1&status=requested&_include=Task:focus"

# B-01  free CT slots for a service
curl "$REF/Slot?schedule.actor=HealthcareService/qhc-hcs-f1-ct&status=free"

# S-01  track the referral
curl "$REF/Task?focus=ServiceRequest/qhc-sr-0001"
curl "$REF/Appointment?based-on=ServiceRequest/qhc-sr-0007"

# P-01  AU Patient Summary document for a patient with history (stretch)
curl "$REF/Patient/qhc-pat-01/\$summary"

Patient summary (AU PS $summary)

The Referral Server can produce an AU Patient Summary document on demand (test case P-01, stretch). It is HAPI's built-in IPS module with the AU PS plugin (hapi-fhir-au-ps), so a document is built from the patient's Conditions, AllergyIntolerances, MedicationRequests/Statements, Procedures and Observations.

curl "$REF/Patient/qhc-pat-01/\$summary"                       # by id
curl "$REF/Patient/\$summary?identifier=<system>|<value>"       # by business identifier

The result is a document Bundle that declares http://hl7.org.au/fhir/ps/StructureDefinition/au-ps-bundle, with the Composition first. Sections you will see: Allergies and Intolerances, Medication List, Problem List (always present), and History of Procedures, Diagnostic Results, Vital Signs, History of Past Illness and Pregnancy Information when the patient has matching data. qhc-pat-01 returns, for example, 1 allergy, 2 medications, 3 problems, 1 procedure, 3 results and 1 vital sign.

  • Patients without history (qhc-pat-03, -08, -09, -15, -16) still get the three required sections, each holding one generated "no information" entry. The sections do not use emptyReason.
  • The first call after a server restart takes about ten seconds, later ones about half a second.
  • Data you have just written can take up to a minute to show up. HAPI reuses identical searches for 60 seconds, and $summary runs searches internally.
  • The server does not validate the document against the AU PS profiles. The profile is declared in meta.profile only. Relative references inside the document (for example Composition.subject) resolve to entries with absolute fullUrls, which a strict validator flags.

Things worth knowing

These came from running the collection against the live servers.

  • Endpoint has no organization search parameter. Endpoint?organization=… quietly returns nothing. Reach Endpoints from the owner instead: HealthcareService?_id=…&_include=HealthcareService:endpoint or Organization?_id=…&_include=Organization:endpoint.
  • Seeded Endpoint.address values are in-cluster URLs (http://fhir.track2.svc.cluster.local:8080/fhir). From your laptop, use the public referral URL above instead.
  • The server does not prevent double booking. Two Appointments can be created against the same Slot and both succeed. A booking client must re-read the Slot and check status = free immediately before booking, and the filler must set the Slot to busy when it confirms (request B-02 does both steps). This is the interesting part of test case B-03.
  • Triage and booking updates use JSON Patch (PATCH with Content-Type: application/json-patch+json), so you only send what changes. A full PUT works too.
  • Group Task and fulfilment Task. A referral has two Tasks: the Group Task (no focus) and the fulfilment Task, which has focus → ServiceRequest and partOf → Group Task. Search on Task?focus= finds the fulfilment Task only.
  • owner:identifier is not supported on Task search. Search by the organisation's resource id (owner=qhc-org-fill1).
  • The first $validate can take about ten seconds while HAPI warms its validation cache.
  • Directory search parameters are Day-1 assumptions. The ADHA HCPD technical specification is not published yet, so treat D-02 and D-03 as provisional.

fhir-frog conformance tests

fhir-frog is the FHIR conformance test toolkit used to check this track. Tests are FHIR TestScript resources run by frog-runner, deployed here at https://conformance.efiq.hospservices.net.

The test library. QH-Track2-frog-testscripts.zip holds the TestScripts and fixtures for the scenario, as deployed on the conformance host:

Bundle Server Covers
scenario1/step1/ directory Step 1: HealthcareService search
scenario1-referral/ referral Steps 2 to 6: create and submit a referral, retrieve it with supporting information, update and monitor fulfilment status, patient view

These were adapted from the HL7 AU Sparked Testing Event TestScripts (Connected Scenario 1). They cover the referral flow; the Schedule, Slot and Appointment booking steps (B-01 … B-04) are covered by the Postman collection above, not yet by frog TestScripts. Source and run notes: deploy/frog-tests.

Run them on the conformance host (use the in-cluster server URLs, because the runner's JVM does not trust the public certificate chain):

FROG=https://conformance.efiq.hospservices.net

# directory, step 1
curl -s -X POST "$FROG/api/v1/runs" -H 'Content-Type: application/json' -d '{
  "bundlePath": "/bundles/scenario1/step1",
  "serverUrl": "http://directory:8080/fhir"}'

# referral, steps 2 to 6 (needs the IG for profile validation, takes 5 to 10 minutes)
curl -s -X POST "$FROG/api/v1/runs" -H 'Content-Type: application/json' -d '{
  "bundlePath": "/bundles/scenario1-referral",
  "serverUrl": "http://fhir:8080/fhir",
  "igPackage": "hl7.fhir.au.ereq#1.0.1",
  "terminologyServerUrl": "https://r4.ontoserver.csiro.au/fhir"}'

curl -s "$FROG/api/v1/runs/<id>"     # status COMPLETED, every result.success == true

Profile validation runs inside frog-runner from the igPackage you pass, not on the server, so always send both serverUrl and igPackage for the referral bundle. Run one at a time, and expect the referral bundle to leave a few test resources behind (deploy/frog-tests/cleanup-fixtures.py removes them).

Write your own tests, with AI help. The fhir-frog MCP server and skill let Claude, Kiro and other MCP clients author, lint and validate TestScripts for you (release v0.1.0, Java 17+ or Docker). Start with frog_doctor.
